# 网格模型编辑器 — 技术实现说明

## 一、系统架构概述

本项目是一个基于 **WebGL** 的多边形网格模型可视化编辑器，使用 **Three.js (r160)** 作为渲染框架，在单个 HTML 文件 (`index.html`) 中实现了全部功能。核心渲染管线如下：

```
Flower.ply (二进制PLY文件)
      │  PLYLoader 解析
      ▼
BufferGeometry (194,818 顶点, 389,632 三角面片)
      │  computeVertexNormals() 计算法线
      │  居中 + 归一化缩放
      ▼
┌─────────────────────────────────────────────┐
│  场景对象 (Scene Objects)                     │
│  ├── Points        ─ 顶点渲染               │
│  ├── LineSegments   ─ 线框渲染               │
│  ├── Mesh (solid)   ─ 面绘制 (自定义着色器)   │
│  └── Mesh (occlusion) ─ 消隐用遮挡体         │
└─────────────────────────────────────────────┘
      │  WebGL Render Loop (60fps)
      ▼
    屏幕输出
```

## 二、模型加载与预处理

### 2.1 PLY 文件解析

`Flower.ply` 是 **binary_little_endian** 格式的 PLY 文件，包含：

| 元素 | 数量 | 属性 |
|------|------|------|
| vertex | 194,818 | float x, y, z |
| face | 389,632 | list uchar int vertex_indices |

使用 Three.js 内置的 `PLYLoader` 解析二进制数据，自动构建 `BufferGeometry`，其中：
- `position` 属性：`Float32Array`，每个顶点 3 个浮点数 (x, y, z)
- `index` 属性：面片索引，每个三角面 3 个整数索引

### 2.2 法线计算

PLY 文件中**不包含法线数据**，因此调用 `geometry.computeVertexNormals()` 自动计算：

1. 对每个三角面片，计算**面法线**：取两条边的叉积并归一化

$$\vec{n}_{face} = \text{normalize}\left((\vec{v}_1 - \vec{v}_0) \times (\vec{v}_2 - \vec{v}_0)\right)$$

2. 对每个顶点，将其所属的所有面的面法线**累加**
3. 对累加结果**归一化**，得到顶点法线（即面法线的面积加权平均）

$$\vec{n}_{vertex} = \text{normalize}\left(\sum_{f \in \text{adj}(v)} \vec{n}_f\right)$$

这种方法产生的法线是**面积加权**的平均法线，使得大面片对法线的贡献更大，视觉效果自然。

### 2.3 居中与归一化

```javascript
// 1. 计算包围盒中心，平移至原点
geometry.computeBoundingBox();
const center = new THREE.Vector3();
geometry.boundingBox.getCenter(center);
geometry.translate(-center.x, -center.y, -center.z);

// 2. 等比缩放，使最大维度为 2.0
const size = new THREE.Vector3();
geometry.boundingBox.getSize(size);
const maxDim = Math.max(size.x, size.y, size.z);
const s = 2.0 / maxDim;
geometry.scale(s, s, s);
```

这确保无论原始模型尺寸如何，始终在相机视野内正确显示。

## 三、显示模式实现

### 3.1 线框 · 非消隐（Wireframe without Hidden Line Removal）

**原理**：关闭 WebGL 深度测试 (`depthTest: false, depthWrite: false`)，使所有边和顶点均被绘制，无论是否被模型其他部分遮挡。

```
渲染对象:  WireframeGeometry → LineSegments
深度测试:  关闭
效果:      模型的所有三角形边全部可见，包括背面和被遮挡的边
```

`WireframeGeometry` 将每个三角面的 3 条边提取为独立线段（共 389,632 × 3 = 1,168,896 条线段）。

### 3.2 线框 · 消隐（Wireframe with Hidden Line Removal）

**原理**：利用 **Z-Buffer（深度缓冲）** 算法实现隐藏线去除。分两步渲染：

```
第一步 (renderOrder = -1):
  渲染"遮挡体" ─ 与模型同形状的实体网格，颜色设为背景色 (0x0d1117)
  启用 polygonOffset 将深度值略微推远
  → 填充深度缓冲区，但视觉上不可见

第二步 (renderOrder = 1):
  渲染线框 ─ 启用深度测试 (depthTest: true)
  → 线框片段与深度缓冲比较：
     · 可见的边 → 通过深度测试 → 绘制
     · 被遮挡的边 → 深度测试失败 → 丢弃
```

**为何使用 `polygonOffset`？** 线框的几何位置与实体表面完全重合，直接进行深度测试会产生 **Z-fighting**（深度值精度不足导致的闪烁）。`polygonOffset` 将遮挡体的深度值在硬件层面微调偏远，确保表面上的线框始终"略靠前"于遮挡体，从而正确通过深度测试。

### 3.3 面绘制（Surface Rendering）

使用自定义 GLSL 着色器渲染三角面片，支持 Gouraud 和 Phong 两种明暗处理（详见第四节）。

如果同时勾选了"显示边"，线框会叠加在面绘制之上，同样依赖 `polygonOffset` + `renderOrder` 避免 Z-fighting。

## 四、光照模型详解

### 4.1 计算空间：视图空间（View Space / Eye Space）

所有光照计算在**视图空间**中进行。在视图空间中：
- 相机位于原点 $(0,0,0)$
- 观察方向沿 $-Z$ 轴
- 光源位置 $\vec{L}_{pos}$ 在每一帧从世界空间转换到视图空间

```javascript
// 每帧将世界空间光源位置转换为视图空间
_lightView.copy(lightWorldPos).applyMatrix4(camera.matrixWorldInverse);
```

选择视图空间的优势：观察向量 $\vec{V}$ 可以简单地取为 $\text{normalize}(-\vec{P}_{view})$，无需额外传递相机位置。

### 4.2 Phong 反射模型（Phong Reflection Model）

本项目实现的是经典 **Phong 反射模型**（Bui Tuong Phong, 1975），将表面反射的光分解为三个独立分量的线性叠加：

$$I = I_{ambient} + I_{diffuse} + I_{specular}$$

#### (a) 环境光分量（Ambient）

$$I_{ambient} = k_a \cdot C_{base}$$

- $k_a = 0.15$：环境光强度系数（`uAmbientStr`）
- $C_{base}$：物体基础颜色

**物理含义**：模拟场景中经过多次反弹后均匀分布的间接光照。这是一个**极度简化的常数近似**——真实场景中的间接光照（全局光照）分布复杂且与几何形状有关，但计算代价高昂。环境光项以极低成本避免了完全黑暗的阴影区域。

**对应 GLSL 代码**：
```glsl
c += uBaseColor * uAmbientStr * uUseAmbient;
```

#### (b) 漫反射分量 — Lambert 模型（Diffuse）

$$I_{diffuse} = C_{base} \cdot \max(\vec{N} \cdot \vec{L},\ 0)$$

- $\vec{N}$：表面法线（归一化）
- $\vec{L}$：从着色点指向光源的方向（归一化）
- $\max(\cdot, 0)$ 确保背光面不产生负值贡献

**物理含义**：Lambert 余弦定律（Johann Heinrich Lambert, 1760）指出，理想漫反射表面（Lambertian surface）反射的光强与入射光和法线夹角的余弦成正比。这模拟了光线被粗糙表面均匀散射的行为——无论从哪个角度观察，同一点的漫反射亮度相同。

**物理真实性**：Lambert 模型对**哑光、粗糙**表面（如粉笔、未上漆的木头）是相当准确的近似。但它忽略了：
- 菲涅尔效应（掠射角度下反射率升高）
- 次表面散射（光进入材质内部再射出）
- 微表面结构的自遮挡

**对应 GLSL 代码**：
```glsl
float diff = max(dot(N, L), 0.0);
c += uBaseColor * diff * uUseDiffuse;
```

#### (c) 镜面反射分量 — Phong 高光模型（Specular）

$$I_{specular} = C_{spec} \cdot \max(\vec{V} \cdot \vec{R},\ 0)^{n}$$

其中反射向量 $\vec{R}$ 的计算为：

$$\vec{R} = 2(\vec{N} \cdot \vec{L})\vec{N} - \vec{L} = \text{reflect}(-\vec{L}, \vec{N})$$

- $\vec{V}$：从着色点指向观察者（相机）的方向
- $\vec{R}$：光线关于法线的镜面反射方向
- $n$：光泽度指数（`uShininess`，范围 1~128）
- $C_{spec}$：高光颜色（默认白色）

**物理含义**：模拟光滑表面的镜面高光。当观察方向 $\vec{V}$ 接近完美反射方向 $\vec{R}$ 时，$\vec{V} \cdot \vec{R} \approx 1$，产生明亮的高光点。指数 $n$ 控制高光的"锐利度"：

| $n$ 值 | 效果 | 对应材质 |
|--------|------|----------|
| 1~5 | 宽而模糊的高光 | 粗糙金属 |
| 10~30 | 中等高光 | 塑料、皮肤 |
| 50~128 | 锐利的小光斑 | 抛光金属、玻璃 |

**物理真实性**：Phong 高光模型是一个**经验模型**（empirical model），并非基于物理推导。它的主要局限：

1. **不满足能量守恒**：增大 $n$ 会使高光变窄，但峰值不变，导致总反射能量随 $n$ 减小。物理正确的做法需要一个归一化因子 $\frac{n+2}{2\pi}$。
2. **余弦幂衰减不真实**：真实材质的 BRDF（双向反射分布函数）并非简单的余弦幂形式。
3. **忽略菲涅尔效应**：真实材质在掠射角度（$\vec{V}$ 接近表面切线方向）时镜面反射率急剧增大（Fresnel 方程），Phong 模型忽略了这一点。
4. **Blinn-Phong 更常用**：实际工业界更常使用 Blinn-Phong 变体，用半程向量 $\vec{H} = \text{normalize}(\vec{L}+\vec{V})$ 替代反射向量，计算 $(\vec{N} \cdot \vec{H})^n$，更高效且在掠射角度表现更好。

**对应 GLSL 代码**：
```glsl
vec3 R = reflect(-L, N);
float spec = pow(max(dot(V, R), 0.0), uShininess);
c += uSpecColor * spec * uUseSpecular;
```

### 4.3 三分量的完整组合

在着色器中，三个分量可以独立开关，通过 `float` 类型的开关变量（0.0 或 1.0）进行无分支控制：

$$I_{final} = \text{clamp}\Big(\underbrace{k_a \cdot C_{base}}_{\text{ambient}} \cdot s_a + \underbrace{C_{base} \cdot (N \cdot L)}_{\text{diffuse}} \cdot s_d + \underbrace{C_{spec} \cdot (V \cdot R)^n}_{\text{specular}} \cdot s_s,\ \ 0,\ 1\Big)$$

其中 $s_a, s_d, s_s \in \{0, 1\}$ 分别为环境光、漫反射、镜面反射的开关。

## 五、明暗处理（Shading）

明暗处理决定了**在哪里计算光照**——在顶点上还是在每个像素上。这与光照模型（Phong 反射模型）是正交的概念。

### 5.1 Gouraud 明暗处理（Gouraud Shading, 1971）

**计算位置**：顶点着色器（Vertex Shader）

**流程**：

```
顶点着色器:
  对每个顶点 → 使用 Phong 反射模型计算完整光照颜色
  → 输出 vColor (varying)

光栅化阶段:
  三角形内部的每个像素 → 对三个顶点的 vColor 进行重心插值

片段着色器:
  直接输出插值后的颜色 → gl_FragColor = vec4(vColor, 1.0)
```

**优点**：计算量小（只在顶点处计算光照，三角网格有 194K 顶点）

**缺点**：
- 高光可能丢失：如果高光的中心落在三角形内部而非顶点上，颜色插值会将其"抹平"
- 马赫带效应：相邻三角形之间的颜色梯度不连续，视觉上出现明暗带

### 5.2 Phong 明暗处理（Phong Shading, 1975）

**计算位置**：片段着色器（Fragment Shader）

**流程**：

```
顶点着色器:
  对每个顶点 → 输出法线 vNormal 和视图空间位置 vViewPos (varying)

光栅化阶段:
  三角形内部的每个像素 → 对三个顶点的法线进行重心插值

片段着色器:
  对每个像素:
    1. 将插值后的法线重新归一化: N = normalize(vNormal)
    2. 使用 Phong 反射模型计算完整光照
    3. 输出最终颜色
```

**关键步骤**：插值后的法线需要**重新归一化**。线性插值两个单位向量的结果通常不是单位向量（例如两个 45° 法线插值到中间时，模长为 $\cos(22.5°) \approx 0.924$）。

**优点**：
- 高光精确：每个像素独立计算，不会丢失高光细节
- 过渡平滑：法线的逐像素插值消除了马赫带效应

**缺点**：
- 计算量大：需要为每个像素执行完整光照计算。对于 389K 三角面片的模型，在 1080p 分辨率下，可见像素可达百万级别。但现代 GPU 的并行计算能力完全可以实时处理这一规模。

### 5.3 两者对比

| 特性 | Gouraud | Phong |
|------|---------|-------|
| 光照计算位置 | 顶点着色器 | 片段着色器 |
| 插值内容 | 颜色 (RGB) | 法线 (vec3) |
| 高光表现 | 可能丢失或变形 | 准确锐利 |
| 视觉质量 | 较低（网格稀疏时明显） | 较高 |
| 计算开销 | 较低（顶点数级别） | 较高（像素数级别） |
| 适用场景 | 实时性要求极高的老旧硬件 | 现代实时渲染的标准方案 |

## 六、消隐算法（Hidden Surface Removal）

### 6.1 Z-Buffer 算法

本项目使用 WebGL 内置的 **Z-Buffer（深度缓冲）** 算法，这是目前最广泛使用的消隐方法。

**原理**：
1. 为每个像素维护一个深度值（Z-Buffer），初始化为最远距离
2. 光栅化每个三角面片时，对每个覆盖的像素：
   - 计算该片段的深度值 $z$
   - 与 Z-Buffer 中已有值比较
   - 若 $z <$ 已有值（更近），更新颜色缓冲和深度缓冲
   - 若 $z \geq$ 已有值（更远或相同），丢弃该片段

**复杂度**：$O(n)$，其中 $n$ 为需光栅化的片段总数。无需对几何体排序。

### 6.2 消隐线框的实现

针对线框消隐模式，利用了 Z-Buffer 的特性进行两遍渲染（Two-Pass Rendering）：

**第一遍**：渲染背景色实体（`occlusionMesh`）
- `renderOrder = -1`（先渲染）
- 颜色 = 背景色 `0x0d1117`（视觉上不可见）
- `polygonOffset: true`（深度值向远处偏移，避免 Z-fighting）
- 作用：在深度缓冲中"刻下"模型的轮廓

**第二遍**：渲染线框（`wireObj`）
- `renderOrder = 1`（后渲染）
- `depthTest: true`（开启深度测试）
- 被模型自身遮挡的线段因深度测试失败而被剔除

### 6.3 Polygon Offset 原理

`polygonOffset` 是 OpenGL/WebGL 提供的硬件功能，对光栅化后的片段深度值做微调：

$$z'= z + \text{factor} \times m + \text{units} \times r$$

- $m$：多边形深度值相对屏幕坐标的最大斜率（与三角形朝向有关）
- $r$：深度缓冲的最小可分辨单位
- 本项目使用 `factor=1, units=1`：将遮挡体的深度略微推远

使用 Three.js 的 `OrbitControls` 插件，实现围绕目标点的轨道相机控制：

## 八、物理真实性总结

### 本项目采用的模型是否物理真实？

**简短回答：不是。** Phong 反射模型是一个**经验性的局部光照模型**，而非基于物理的渲染（Physically Based Rendering, PBR）。但它在计算机图形学教学和实时渲染领域有着重要的历史地位和实用价值。

### 与真实物理的差距

| 方面 | 本项目 (Phong) | 物理真实 (PBR) |
|------|---------------|----------------|
| **能量守恒** | 不满足。出射光能量可能超过入射光 | 严格满足。反射 + 吸收 ≤ 入射 |
| **BRDF** | $\cos^n(\alpha)$ 经验公式 | 基于微表面理论 (GGX/Cook-Torrance) |
| **菲涅尔效应** | 忽略 | Schlick 近似或完整 Fresnel 方程 |
| **金属 vs 非金属** | 不区分 | 金属度参数控制反射行为差异 |
| **粗糙度** | 用 shininess 指数近似 | 微表面法线分布函数 (NDF) |
| **环境光** | 常数近似 | 基于图像的光照 (IBL) / 球谐函数 |
| **全局光照** | 无（仅直接光照） | 光线追踪 / 辐射度方法 |
| **阴影** | 无 | Shadow Map / Ray Tracing |
| **自遮挡** | 无 | 微表面几何项 (Smith G) |

### 为什么仍然使用 Phong 模型？

1. **教学价值**：Phong 模型清晰地展示了光照的三个基本分量（环境、漫反射、镜面），是理解更复杂模型的基础
2. **计算效率**：只需几次点积和一次幂运算，适合实时渲染
3. **视觉可接受**：对于非真实感渲染或对物理精度要求不高的场景，效果足够好
4. **历史意义**：1975 年 Phong 提出此模型时，它是计算机图形学的重大突破，使得计算机首次能生成具有光泽感的图像

## 九、渲染管线总览

```
┌───────────────────────────────────────────────────────────┐
│                    JavaScript (CPU)                        │
│  · 更新 uniform 变量 (光源位置、颜色、开关)                  │
│  · 控制对象可见性、材质切换                                  │
│  · 处理用户输入 (鼠标/键盘)                                 │
│  · 更新相机矩阵                                            │
└──────────────────────┬────────────────────────────────────┘
                       │ drawCall
┌──────────────────────▼────────────────────────────────────┐
│              Vertex Shader (GPU, per-vertex)               │
│  · position → modelViewMatrix → 视图空间坐标 mvPos         │
│  · normal → normalMatrix → 视图空间法线 N                   │
│  · [Gouraud] 在此计算完整光照 → vColor                      │
│  · [Phong]   输出 vNormal, vViewPos 供片段着色器使用         │
│  · 最终: gl_Position = projectionMatrix × mvPos             │
└──────────────────────┬────────────────────────────────────┘
                       │ 光栅化 + 插值
┌──────────────────────▼────────────────────────────────────┐
│             Fragment Shader (GPU, per-pixel)               │
│  · [Gouraud] 直接输出插值后的 vColor                        │
```

## 十一、运行方式

由于浏览器安全策略禁止 `file://` 协议下的 AJAX 请求（无法加载 PLY 文件），需要通过 HTTP 服务器访问：

```bash
cd /home/wtz/桌面/3D_computer_graphics
python3 -m http.server 8080
```

然后在浏览器中打开 http://127.0.0.1:8080/index.html 。
